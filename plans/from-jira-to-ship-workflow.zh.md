# 从 Jira 到交付：工作流

来源：[From Jira to Ship workflow](https://xsolla.atlassian.net/wiki/spaces/OS1/pages/25532235959/From-Jira-to-Ship+workflow)。以下译文依据 2026-11-13 用户提供的英文正文和原文截图；未核对 Confluence 页面的其他内容。

## 文档定位

这是目标工作流的最终指导计划。开发应尽量按此流程实施。若出现无法避免的技术或流程问题，可以偏离本计划；实施者应记录原因、影响和实际采用的做法，并按验证结果更新仓库中的[实施计划](chat-to-fix-agent.md)。本文不表示这些步骤已经实现或验收通过。

## 中文译文

1. 创建 Jira 工单。工单写明需求（Requirement：要求做什么）、目的（Purpose：为什么做）、时间要求（When：可选）和完成定义（Definition of Done：验收标准）。
2. Jira 工单状态变为 `In Progress` 时，调用 AI Agent 处理该工单。
   - **2.a** 根据需求和验收标准创建自动化测试用例 `T1`。锁定供 Agent 使用的用例；必要时允许人工修改。如果验收标准无法测试，Agent 在工单中提出问题，且暂不开始工作。
   - **2.b** 在开发分支修改代码。
   - **2.c** Agent 识别受影响的回归测试集 `T2`。步骤 2.b 与 2.c 并行开始。识别职责见下文补充决策。
   - **2.d** 自动创建 Stage 测试环境。在该环境自动运行 `T1` 和 `T2`，并生成测试结果。
   - **2.e** 如果测试未通过，AI Agent 修复代码，并再次运行相同的测试。
   - **2.f** 修复和测试最多循环三次。循环最终以测试通过或测试失败结束。
3. 如果步骤 2 的最终测试结果通过，AI Agent 将分支变基到 `master`，然后创建 MR，并暂停等待人工代码审查。如果未通过，Agent 将失败日志和 Draft MR 发布到工单，将工单指派给人工开发者，然后退出。
4. 人工开发者确认代码修改后，由 Agent 合并到 `master`。

## 补充决策：Step 2.c 的 T2 选择

2026-11-13，用户补充了原文 `Open Question #1` 的解决方案。写代码的 Agent 不独自决定 `T2`，以免选出过窄、容易通过的回归测试集。

1. 在目标代码仓库保存一份由人工维护的映射文件。该文件记录代码文件与测试套件的对应关系，供选择 `T2` 时使用。Agent 只读取，不修改该文件。文件路径和格式在实施时确定。
2. 使用独立的 Agent 会话选择 `T2`；该会话可以使用不同的 LLM。
3. 一次任务选定 `T2` 后，后续修复和重测只能向 `T2` 增加用例，不得删除已有用例。
4. 在 MR 中列出选定的 `T2`，供审查者核对。
